Chapter 05 · 多视角路由与输出头

承接 Ch.03（cross-attention 怎么算）与 Ch.04（RoPE）：
本章回答最后两个问题 —— ① 那些 context 视角具体怎么组织、为什么分两套 block； ② token 序列最后怎么变成「每像素高斯」和「相机位姿」。
全程仍用「我 / 爱 / 中国」这个玩具例子（3 个视角 × 每视角 3 个 token × 4 维）。

1. 全景：从 Encoder 输出到最终产物

Encoder 输出   feat : [b, v, l, 1024]        # v 个视角，每视角 l=257 个 token，1024 维
                 pos  : [b, v, l, 2]
                      ↓ decoder_embed（Linear 1024 → 768）
Decoder        f     : [b, v, l, 768]
                      ↓ 12 层 DecoderBlock（Self-Attn + Cross-Attn + MLP）
              final_output = [多个尺度的特征]   # 一个 list，每层输出都留着
                      ↓ 三个头并行
   ┌──────────────────┼──────────────────┐
   ↓                  ↓                  ↓
pts3d head      gaussian_param_head   pose head
(b, h, w, 3)    (b, 83, h, w)         (b, 9)
每像素 3D 坐标   → (b, h·w, 83)        → process_pose → (b, 4, 4)
= 高斯的中心     每像素 83 个参数        = 相机外参
   └──────────────────┼──────────────────┘
                      ↓
        每个视角 65536 个高斯（256×256）+ 一个 4×4 位姿
最关键的一句话：高斯不是「一个 token 一个」，而是每个像素一个（256×256 = 65536 个）。 所以 Decoder 末尾必须把 token 序列还原成二维特征图并上采样回原图分辨率 —— 这一步由 DPT 头完成， 它和你在 MiniDiT 里见过的 unpatchify 是同一个目的，但用的是卷积上采样（更平滑，能补足细节）。

2. 多视角路由：谁跟谁配对、谁走哪套 block

用玩具例子：3 个视角（视角 0 / 1 / 2），每个视角 3 个 token（我 / 爱 / 中国），每 token 4 维。

2.1 每个视角的 context 怎么来（已在 Ch.03 学过）

generate_ctx_views（backbone_croco_multiview.py:178-184）：
  把每个视角「复制 v 份」→ 用 mask 去掉对角线（自己不当自己的 context）→ 拼起来

  视角 0 的 context = [视角1 的 3 个 token | 视角2 的 3 个 token] = 6 个 token
  视角 1 的 context = [视角0 的 3 个 token | 视角2 的 3 个 token] = 6 个 token
  视角 2 的 context = [视角0 的 3 个 token | 视角1 的 3 个 token] = 6 个 token

→ 每个视角：Q = 自己的 3 个 token，K/V = 别人的 6 个 token
→ scores 形状 (3, 6) —— 不是方阵

2.1.1 完整矩阵链 —— 纠正一个高频错误：拼接方向

易错点：把「视角1 的 3 个 token」和「视角2 的 3 个 token」横着接成 3×8 → 于是 scores 变成 [3,4] × [8,3]，根本乘不了。
正确：它们是竖着叠（沿 token 维），3+3 = 6 个 token，特征维仍是 4 → 6×4。 
视角 1 的 token:  3 行 × 4 列
视角 2 的 token:  3 行 × 4 列
                    ↓ 竖着叠（token 维相加，特征维不变）
context:          6 行 × 4 列      ← 不是 3×8！

代码证据（第 183 行）：
  ctx_views.flatten(2, 3)   # (b, v, v-1, l, c) → (b, v, (v-1)*l, c)
                            # 只压 token 维 (v-1, l) → (v-1)*l，特征维 c 不动
以视角 0 为例的完整矩阵链：

  视角 0 的 token:   (3, 4)
  context:           (6, 4)

  Q = (3,4) @ W_q(4,4) = (3,4)     ← W_q 来自 blk1
  K = (6,4) @ W_k(4,4) = (6,4)     ← W_k 也来自 blk1（不是 blk2！见 §2.5）
  V = (6,4) @ W_v(4,4) = (6,4)

  scores = Q @ Kᵀ = (3,4) @ (4,6) = (3,6)     ← 3 个 query × 6 个 key ✓ 合法
  attn   = softmax(scores, dim=-1) → (3,6)，每行和 = 1
  out    = attn @ V = (3,6) @ (6,4) = (3,4)   ← 回到「3 个 token × 4 维」

真实维度（v=3、256×256 输入）：
  Q = (257,768)   K = V = (514,768)   scores = (257,514)   out = (257,768)

2.3 一个名字陷阱：_decoder(feat, pose) 里的 pose 其实是坐标

源码里 _decoder(self, feat, pose, ...) 的第三个参数名叫 pose，但它装的不是位姿！
看调用处（backbone_croco_multiview.py:243）： self._decoder(feat[:, :v-target_num_views], pos[:, :v-target_num_views])
传进去的是 pos —— 就是 Ch.01 里那个 [b, v, l, 2] 的网格坐标。 它只是被形参命名成了 pose，一路传给 DecoderBlock 的 xpos / ypos，最终喂给 RoPE（Ch.04）。
真正的位姿是网络「输出」的东西（pose head），不是输入。

2.4 循环 12 层，每层输出都留着

final_output.append(...) 每跑一层就存一份 —— 最后 final_output 是一个 多尺度特征列表（类似 DPT 的 hook）。后面的 DPT 高斯头要的就是这种多层特征 （浅层管细节/边缘，深层管语义），所以它接收的是 [tok[:, i] for tok in dec_feat] ——「第 i 个视角在所有层上的特征」。

2.4.1 context 的刷新时机：特征每层重算，坐标只算一次

186  pos_ctx = generate_ctx_views(pose)                     # 循环【之前】算一次
                                                            # 网格坐标不变 → 算一次就够
187  for blk1, blk2 in zip(self.dec_blocks, self.dec_blocks2):
188      feat_current     = final_output[-1]                 # 上一层的输出（已拼好）
189      feat_current_ctx = generate_ctx_views(feat_current)  # 循环【里面】每层重算
191      f1 = blk1(feat_current[:,0], feat_current_ctx[:,0], ...)   # context 当参数 y 传进去

两个要点：

  1. context 不是 block「存」的 —— 是 decoder 循环在 block 外面现算好， 当成 y 参数传进去的。block 自己不保存任何 context。
  2. 第 i 层的 context = 其他视角在第 i−1 层「更新后」的 token，不是原始 token。 所以视角 0 下一层查到的是「视角 1、2 刚被 blk2 处理过的样子」—— 跨视角对应关系就是这样一层层精炼出来的（这也是为什么要堆 12 层，而不是 1 层）。
信息怎么跨 block 流动：blk1 产出的 f1 与 blk2 产出的 f2 拼回 final_output → 成为下一层的 feat_current → 再 generate_ctx_views → 下一层的 context。
参数各自独立，特征共享流动。

2.5 这套路由的三条铁律（易错点合集）

#铁律常见误解
①拼接沿 token 维（竖着叠）：3+3 → 6 个 token × 4 维 = 6×4 误以为横着接成 3×8，导致 scores 乘不出来（见 §2.1.1）
②W 不跨 block：视角 0 这条链的 W_q / W_k / W_v 全部来自 blk1 误以为「Q 用 blk1 的 W_q、K/V 用 blk2 的 W_k/W_v」
③两套路由规则互相独立（见下表） 把「用哪套权重」和「去查谁」混为一谈

2.5.1 ③ 的两套规则（务必分清）

路由类型规则决定什么会不会变
权重路由
（谁被哪个 block 处理）		 按下标固定：视角 0 → blk1；视角 1..v−1 → blk2
（其余视角共用同一套权重、打包成一批）		 用谁的 W_q / W_k / W_v 永不轮换
context 路由
（谁的 token 当 K/V）		 按排除自己：每个视角的 context = 其他所有视角拼起来 Q 去查谁 每层随特征更新
举例：视角 1 的 cross-attention
Q = 视角 1 自己的 token（被 blk2 处理）
K/V = 视角 0 + 视角 2 的 token —— 其中视角 0 的 token 是上一层 blk1 产出的， 视角 2 的 token 是上一层 blk2 产出的。
→ 所以 context 里混着两个栈的产出，但「用哪套权重处理查询」只由下标决定。

2.5.2 一主多从，不轮换

视角 0            → 永远 blk1（dec_blocks）      ← 参考视角 / 锚点（位姿 = 单位阵）
视角 1, 2, 3, 4…  → 永远 blk2（dec_blocks2）     ← 共用同一套权重，打包成一批

代码（第 191、194 行）：
  f1 = blk1(feat_current[:, 0],  ...)      # 只取下标 0
  f2 = blk2(feat_current[:, 1:], ...)      # 其余全部塞进 batch 维 b×(v−1)
  • 术语别反：视角 0 才是参考 / 锚点视角（reference / anchor） —— 它的预测位姿是单位阵，是所有相对位姿的基准；其余视角是「相对它估计位姿」的视角， 不是"参考视角"。
  • 参数量不随视角数增长：训 2 张图和 8 张图用同一套模型；推理时视角数可任意（我们用 4 张）。
  • 视角 1..v−1 之间置换等变：交换视角 1 和 2 的顺序，结果等价 （共享权重 + context 排除自身）。
  • 同样的「一主多从」在全网出现 4 次：dec_blocks / dec_blocks2、 pose_head / pose_head2、gaussian_param_head / gaussian_param_head2、 _downstream_head(1) / _downstream_head(2)。
小坑：forward 里有 symmetrize_batch 参数（默认 False）， 文件里也 import 了 make_batch_symmetric；若开启会把批次复制并交换角色（DUSt3R 处理两张图时的技巧）。 EcoSplat / SPFSplat 这条路径默认不走 —— 所以我们看到的就是固定分配、不轮换。

3. 输出头 A：pts3d head —— 高斯的「中心」从哪来

254  res1 = self._downstream_head(1, [tok[:, 0] for tok in dec_feat], shape[:, 0])
317  pts_all = torch.stack([r['pts3d'] for r in all_mean_res], dim=1)   # [b, v, h, w, 3]

→ 每个像素一个 3D 坐标 (x, y, z)，直接在【第一视角的坐标系】里给出。

这就是高斯的中心（μ）。不是从 token 反推的，而是网络直接回归出了一张 h × w × 3 的点云图 —— 和 DUSt3R 的 pointmap 是同一个思路。

用玩具例子看

3 个 token（我 / 爱 / 中国），4 维  →  pts3d head  →  每个 token（当成 1 个像素）出 3 个数：

  我   → (0.1, 0.2, 1.5)     ← 这个像素对应的 3D 点
  爱   → (0.4, 0.1, 1.7)
  中国 → (0.7, 0.3, 2.0)

真实情况：256×256 = 65536 个像素，每个出 3 个数 → [b, v, 256, 256, 3]

4.1 DPT 头怎么把 token 变回图像（对比 unpatchify）

你在 MiniDiT 里学过的做法（unpatchify）：
  token (b, N, patch_dim) → reshape 回 (b, C, H, W)    纯变形，无参数，无信息融合

EcoSplat 的做法（DPT）：
  dec_feat（多层 token 列表）
    → 每层重排成 2D 特征图   （16×16 的小图）
    → 卷积 + 上采样，逐层放大（16 → 32 → 64 → … → 256）
    → 层与层之间相加融合（浅层补细节，深层给语义）
    → 输出 (b, 83, 256, 256)

区别：unpatchify 是「拼回去」，DPT 是「画回来」—— 有卷积参数、能补细节、分辨率可变。

玩具例子版

3 个 token（我 / 爱 / 中国），4 维，当成 (1, 3) 的特征图：

  第 1 步 重排：   [我 | 爱 | 中国]   →  1 行 3 列的小图
  第 2 步 上采样： 1×3  →  2×6（真实是 16×16 → 256×256）
  第 3 步 每像素出参数：
      像素(0,0) → 5 个数（玩具版；真实是 83 个）
      像素(0,1) → 5 个数
      …
  第 4 步 第 0 个数 = 密度，其余 = 尺度/旋转/颜色

→ 于是「每个像素一个高斯」，中心来自 pts3d，其余来自这里。

5. 输出头 C：pose head —— 相机位姿怎么出来

encoder_spfsplat.py · 第 288-313 行 
288  pose_res1 = self.pose_head([tok[:, 0] for tok in dec_feat], shape[0, 0])   # (b, 9)
291  pose_res2 = self.pose_head2([tok[:, i] for tok in dec_feat], shape[0, i])   # (b, 9)
308  poses_enc = torch.stack(all_pose_params, dim=1)          # (b, v, 9)
309  pred_extrinsics = self.process_pose(poses_enc, context['index'])   # (b, v, 4, 4)
阶段形状讲解
pose_head 输出(b, 9) 每个视角 9 个数：3 个平移 + 6 个旋转（6D 旋转表示，避免四元数/欧拉角的奇异性）
stack 后(b, v, 9)v 个视角各一套
process_pose(b, v, 4, 4) 把 9 维组装成 4×4 外参矩阵（旋转矩阵由 6D 表示还原，拼接平移向量）
注意 pose_head / pose_head2 又是两套 —— 和 blk1 / blk2、gaussian_param_head / gaussian_param_head2 是同一个规律：第 0 视角单独一套参数，其余视角共享另一套。 因为第 0 视角被当作参考坐标系（pose_make_relative=True）， 它自己的位姿是「单位阵基准」，其余视角回归的是相对它的位姿。

玩具例子

3 个视角的 decoder token → pose head：

  视角 0 → 9 个数 (0,0,0, 1,0,0,0,1,0)  → 4×4 = 单位阵（它就是参考系）
  视角 1 → 9 个数 → 4×4 = 相对视角 0 的外参
  视角 2 → 9 个数 → 4×4 = 相对视角 0 的外参

所以 EcoSplat 是 pose-free 的：它不需要输入位姿，
而是自己在 forward 里把位姿「算出来」（这就是 SPFSplat / NoPoSplat 这一系的核心卖点）。

8. 自测

  1. Decoder 里视角 0 和视角 1..v−1 分别走哪套 block？为什么分两套？
  2. _decoder(feat, pose) 里的 pose 到底是什么？
  3. 高斯的中心 μ 在哪产生？在那 83 个数里吗？
  4. 83 个数分别是什么？每个视角总共产生多少个高斯（256×256 时）？
  5. pose head 输出几个数？怎么变成 4×4 矩阵？为什么说 EcoSplat 是 pose-free 的？
答案

1. 视角 0 走 blk1（dec_blocks），视角 1..v−1 打包成一批走 blk2（dec_blocks2）。因为视角 0 是参考视角（相对位姿的基准），单独一套参数精算；其余共享以省参数并支持批量。

2. 不是位姿，是 pos —— [b, v, l, 2] 的网格坐标，只是形参名叫 pose。真正的位姿是输出（pose head）。

3. 中心 μ 由 pts3d head（_downstream_head）给出，形状 [b, v, h, w, 3]；不在 83 个数里。

4. 第 0 个是密度（过 sigmoid），剩下 82 个是尺度/旋转/球谐颜色/不透明度等。256×256 时每视角 65536 个高斯。

5. 每视角 9 个数（3 平移 + 6 旋转的 6D 表示），process_pose 组装成 4×4。因为它不需要输入位姿、而是自己算出位姿，所以是 pose-free。
