Supplement · PatchEmbedDust3R 逐行精讲

EcoSplat 学习笔记 · Chapter 01「输入与预处理」§4 切块的完整展开
内容：逐行代码 → 依赖代码（self.proj / PositionGetter）→ 卷积图解 → pos 图解 → 没有 CLS token
开宗明义：这个类里有三个「没有」（都是相对标准 ViT / CLIP 而言，容易踩坑）：
  1. 没有 CLS token —— 它只输出 256 个 patch token，一个不多。你看到的 257 是后面拼的内参/位姿 token，不是 CLS（§7 专门讲）
  2. 没有绝对位置编码 —— 不往 x 上加 pos_embed，位置信息走 RoPE（curope CUDA kernel）
  3. 没有 nn.Linear —— 投影是用 Conv2d(kernel=stride=16) 实现的，数学上等价于线性投影

1. 这个类的职责

一句话：把一张图切成不重叠的小块，每块压成一个向量（token），同时算出每块的网格坐标。

输入  x   : [B, 3, H, W]      # B = b × v（batch 与视角已展平），已归一化到 [-1,1]
输出  x   : [B, N, C]         # N = (H/16)×(W/16) 个 token，每个 C=1024 维
输出  pos : [B, N, 2]         # 每个 token 的网格坐标 (row, col)，int64

2. 主类逐行精讲

因为 kernel == stride == 16，窗口不重叠地滑动，等价于「切块 + 线性投影」（§4 图解）。

  x = x.flatten(2).transpose(1, 2)		flatten(2)：把最后两维 (16,16) 摊平 → [B, 1024, 256]
transpose(1,2)：换成 [B, 256, 1024]，标准 BNC 序列格式。
展平是行优先：第 0 行 16 个 → 第 1 行 16 个……空间邻域保留在序列顺序里。
self.flatten 默认 True；若为 False 则保持 [B,1024,16,16] 给需要 2D 特征图的 head。

2.1 逐字拆开：第 25–28 行里的每一个名字

这三行里出现了 7 个你可能不认识的东西。先记住此刻 x 的形状（第 24 行 self.proj 之后）： [B, 1024, 16, 16]，四个维度依次是 dim0 = B、dim1 = C = 1024、dim2 = H' = 16、dim3 = W' = 16。 下面所有下标都从 0 开始数。

名字它是什么在这里干了什么 / 出来什么
x.size(2)
x.size(3)		 tensor 的取尺寸方法，完全等价于 x.shape[2] 取第 2 维和第 3 维 → 都是 16（网格的高、宽）。
⚠️ 是 proj 之后的 16，不是原图 256 —— 切完块才有 16×16 个格子，坐标也是按格子给的。
x.device tensor 的设备属性，值是 cuda:0 或 cpu 之类 传给 position_getter，好让新建的 pos 建在同一块显卡上。
不这么做的话，后面两个张量一运算就会报「Expected all tensors to be on the same device」。
self.position_getter(...) 一个对象被当成函数调用 —— 因为它类里写了 __call__ 方法 实际执行的是 PositionGetter.__call__(B, 16, 16, device)。
返回 [B, 256, 2] 的网格坐标（下面 2.3 单独拆开讲）。
self.flatten 一个普通的 True / False 开关（__init__ 里存的 bool 变量，不是函数） 默认 True（blocks.py:224 的参数 flatten=True）。
为 True 才执行下面那行展平；为 False 就保持 [B,1024,16,16]，留给需要二维特征图的下游 head。
所以 if self.flatten: 只是个开关判断，没有别的玄机。
x.flatten(2) 摊平方法。参数 2 是 start_dim = 从第 2 维起，后面全部合并成一维 [B, 1024, 16, 16] → [B, 1024, 256]。
前两维 (B, C) 原封不动，把 (16, 16) 拉成 256。
.transpose(1, 2) 交换两个维度。注意不是线性代数里的「矩阵转置」，只是换轴顺序 [B, 1024, 256] → [B, 256, 1024]：
把「通道数 1024」换到最后一维，让每个 token 的 1024 个数连在一起，这才是 Transformer 要的 BNC 格式。
self.norm(x) nn.LayerNorm(1024) 模块被调用（同样靠 __call__） 对最后一维那 1024 个数做归一化，形状不变 → 仍是 [B, 256, 1024]。
公式：y = γ ⊙ (x − μ) / σ + β，逐 token 独立算（和 batch 无关，这点和 BatchNorm 不一样）。

2.2 用一个 2 行 3 列的小网格，亲手走一遍

把通道数缩到 2、网格缩到 2×3（真模型是 1024 和 16×16，道理完全一样）：

输入 x 形状 = [1, 2, 2, 3]：

      通道 0                通道 1
      [ 1   2   3 ]         [ 10  20  30 ]
      [ 4   5   6 ]         [ 40  50  60 ]

① x.flatten(2)  →  形状 [1, 2, 6]
     通道 0 那一行 = [1, 2, 3,  4,  5,  6]
     通道 1 那一行 = [10, 20, 30, 40, 50, 60]
     ↑ 行优先：先数完第 0 行的 3 个，再数第 1 行的 3 个

② .transpose(1, 2)  →  形状 [1, 6, 2]，即 6 个 token、每个 2 维
     token0 = [1, 10]      ← 它来自网格位置 (0,0)
     token1 = [2, 20]      ← (0,1)
     token2 = [3, 30]      ← (0,2)
     token3 = [4, 40]      ← (1,0)
     token4 = [5, 50]      ← (1,1)
     token5 = [6, 60]      ← (1,2)

③ position_getter(1, h=2, w=3, device) 内部：
     torch.arange(w=3)            → [0, 1, 2]
     torch.arange(h=2)            → [0, 1]
     torch.cartesian_prod(y, x)   → (0,0) (0,1) (0,2) (1,0) (1,1) (1,2)
                                    ↑ 正好 6 个，顺序与上面 token0..token5 一一对应 ✓
     再 .view(1, 6, 2).expand(1, -1, 2).clone()  →  pos 形状 [1, 6, 2]

⭐ 最关键的一点：pos 的第 i 个坐标永远对得上 x 的第 i 个 token，
   因为【摊平】和【生成坐标】都是行优先 —— 这是两者能配对的全部原因。

2.3 PositionGetter 内部：5 个函数逐个认识

src/model/encoder/backbone/croco/blocks.py · 第 207–219 行 
207  class PositionGetter(object):          # 注意：不是 nn.Module，没有可学习参数
210      def __init__(self):
211          self.cache_positions = {}       # 空字典，用来缓存
213      def __call__(self, b, h, w, device):     # ← 有了它，对象才能被当函数调用
214          if not (h,w) in self.cache_positions:     # 这个分辨率没算过才算
215              x = torch.arange(w, device=device)
216              y = torch.arange(h, device=device)
217              self.cache_positions[h,w] = torch.cartesian_prod(y, x)   # 形状 (h, w, 2)
218          pos = self.cache_positions[h,w].view(1, h*w, 2).expand(b, -1, 2).clone()
219          return pos
函数 / 写法一句话解释本例（h=w=16, B）下的结果
torch.arange(n) 生成一串整数 [0, 1, 2, …, n-1] arange(16) → [0,1,…,15]，就是行号 / 列号本身
torch.cartesian_prod(y, x) 笛卡尔积：y 的每个值和 x 的每个值两两配对，输出 (h*w, 2)，每行是 (行号, 列号) 16×16 = 256 行，形如 (0,0) (0,1) … (15,15)
.view(1, h*w, 2) 换个看法（不改数据，只改形状标记） [16,16,2] → [1, 256, 2]，多出一个 batch 维
.expand(b, -1, 2) 把长度为 1 的维度复制成 b 份；-1 表示「这一维别动」。
只是视图，不真的多占显存		 [1,256,2] → [B, 256, 2]，B 个视角共用同一套坐标
.clone() 把上面的「视图」真拷一份成独立张量，避免后续就地修改时互相串味 形状不变，但变成自己的内存
cache_positions 一个普通字典做缓存：同一个 (h,w) 只算一次 256×256 和 512×512 各算一次，之后每个 batch 直接取
为什么顺序必须是 flatten → transpose → norm？先 norm 行不行？

不行，是被形状逼出来的。LayerNorm(1024) 里的 1024 是写死的，它只认最后一维：

  • flatten(2) 之后是 [B, 1024, 256]，最后一维是 256 → 此时 norm 会因尺寸对不上而报错（或归一化错对象）。
  • transpose(1,2) 之后是 [B, 256, 1024]，最后一维才是 1024 → 这时候 norm 才对得上。

另外提醒：self.norm 来自 blocks.py:235，norm_layer(embed_dim) if norm_layer else nn.Identity()。 如果构造时没传 norm_layer，它就是 nn.Identity() —— 一个「什么都不做、原样返回」的占位模块，这样第 247 行的代码不用写 if 分支。

5. 依赖代码 ②：PositionGetter（pos 从哪来、是什么）

206  # patch embedding
207  class PositionGetter(object):
208      """ return positions of patches """
210      def __init__(self):
211          self.cache_positions = {}
213      def __call__(self, b, h, w, device):
214          if not (h,w) in self.cache_positions:
215              x = torch.arange(w, device=device)

行代码讲解
207class PositionGetter(object)注意：继承 object，不是 nn.Module。它没有可学习参数，纯粹是按规则算出的一张坐标表。

6. 完整数值实例

设定：b=1，v=4（4 张 context 图），图像 256×256，ViT-Large（embed_dim=1024），patch=16

backbone 先把 [b, v, 3, 256, 256] 展平 → B = b*v = 4

x   : [4, 3, 256, 256]          输入
      ↓ self.proj  Conv2d(3→1024, k=s=16)
      [4, 1024, 16, 16]         256 个格子，每格 1024 通道
      ↓ flatten(2).transpose(1,2)
      [4, 256, 1024]            256 个 token
      ↓ self.norm (LayerNorm 1024)
      [4, 256, 1024]            ← 返回 x

pos : [4, 256, 2]               ← 返回 pos（int64，值域 0..15）

回到 backbone 后再 rearrange 回 [b, v, 256, 1024]

7. 重点：这里没有 CLS token

拼 token 的代码在 backbone_croco_multiview.py 的 _encode_image 里：

146  if intrinsics_embed is not None:
148      if self.intrinsics_embed_type == 'linear':
149          x = x + intrinsics_embed                     # 广播加到每个 token 上（token 数不变）
150      elif self.intrinsics_embed_type == 'token':
151          x = torch.cat((x, intrinsics_embed), dim=1)  # ← 拼 1 个新 token → 257
152          add_pose = pos[:, 0:1, :].clone()
153          add_pose[:, :, 0] += (pos[:, -1, 0].unsqueeze(-1) + 1)
154          pos = torch.cat((pos, add_pose), dim=1)      # ← pos 也跟着 +1，保持对齐
所以：
  • PatchEmbedDust3R 本身永远输出 256 个 patch token，没有 CLS。
  • Cross-attention 里看到的 k/v = 514，是两个视角的 token 拼起来：257 × 2 = 514。
  • 而每个视角的 257 = 256 个 patch + 1 个内参/位姿 token。若配置 intrinsics_embed_loc='none'（默认），就只有 256。

8. 兄弟类：ManyAR_PatchEmbed（一句话）

同文件第 32–70 行还有个 ManyAR_PatchEmbed，专门处理非正方形 / 竖图： 它接收 true_shape，把竖图转置成横图再切块，并单独处理 pos 的横竖顺序。 默认配置用的是 PatchEmbedDust3R（BackboneCrocoCfg.patch_embed_cls 第 54 行）， 所以只有非正方形场景才会用到它。

9. 自测

  1. 输入 [4, 3, 256, 256]，经过 self.proj 后形状是什么？
  2. pos 的形状和 dtype？它的两个分量分别代表什么？
  3. 为什么 kernel_size == stride == 16 就能等价于「切块」？
  4. 本类输出多少个 token？有没有 CLS？
  5. 你在调试时看到 q.shape = [..., 257, ...]，这个 257 是怎么来的？
答案

1. [4, 1024, 16, 16]。输出空间尺寸 = (256 − 16)/16 + 1 = 16；通道数 = embed_dim = 1024。

2. [4, 256, 2]，dtype int64。pos[...,0] 是 row（第几行，0..15），pos[...,1] 是 col（第几列）。

3. 因为步长等于核大小，卷积窗口每次刚好跳过一个核的宽度，不重叠也无缝隙地铺满图像；每个窗口覆盖 16×16×3=768 个值，卷积核（view 成 [1024, 768] 后）就等价于把这 768 维线性投影到 1024 维。

4. 256 个（= (256/16)²），没有 CLS token。

5. 256 个 patch token + 1 个内参（或位姿）token，在 _encode_image 里用 torch.cat(..., dim=1) 拼上去的（intrinsics_embed_type='token' 分支）。不是 CLS。
